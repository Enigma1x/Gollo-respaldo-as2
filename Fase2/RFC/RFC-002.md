# Gestión de Cambios — RFC Documentada

## RFC-002 — Corrección de la Responsabilidad de Registrar Reclamos

| Campo | Detalle |
|---|---|
| **Número de RFC** | RFC-002 |
| **Solicitante** | Steven Miranda Esquivel |
| **Fecha de solicitud** | 6 de agosto de 2026 |
| **Estado** | Pendiente de aprobación |
| **Prioridad** | Media |
| **Impacto estimado** | Bajo |

## 1. Descripción

En los mockups y el flujo original se indicó:

```text
Cliente registra un reclamo
```

Esto contradice el catálogo, RF-01 y HU2, donde el Cliente reporta la falla y el Asesor de Tienda registra el reclamo.

## 2. Inconsistencia

| Artefacto | Responsabilidad |
|---|---|
| Flujo original de mockups | Cliente registra el reclamo |
| UML de actores y funciones | Cliente asociado a Registrar reclamo |
| Catálogo de actores | Cliente reporta la falla |
| RF-01 | Asesor de Tienda registra |
| HU2 | Asesor de Tienda registra |

## 3. Justificación

El registro interno requiere validar datos, factura, producto y garantía, crear el expediente y generar un número único. Estas tareas corresponden al Asesor de Tienda.

## 4. Cambio propuesto

Sustituir:

```text
Cliente registra un reclamo
```

Por:

```text
Cliente reporta la falla o solicita la garantía
        ↓
Asesor de Tienda registra el reclamo
```

También se propone:

- Asociar `Registrar reclamo` al Asesor de Tienda.
- Asociar al Cliente `Solicitar garantía`, `Consultar estado` y `Recibir notificaciones`.
- Indicar que la pantalla de registro es interna.
- Agregar `id_asesor` al modelo de datos.

## 5. Partes afectadas

- Mockups funcionales.
- Flujo principal.
- UML de actores y funciones.
- Modelo entidad–relación.
- Diccionario de datos.
- Matriz de trazabilidad.

## 6. Opciones

### Opción A — Recomendada

Mantener RF-01 y HU2 y corregir mockups, flujo y UML.

### Opción B

Permitir que el Cliente registre directamente, lo cual ampliaría alcance, permisos, validaciones y seguridad.
